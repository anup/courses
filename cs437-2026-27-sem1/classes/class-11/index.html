2. Pick your track

A — you cleared it

Re-running your own code proves nothing you do not already believe. Test somebody else's.

Write a conformance tester. It takes an address, a port and a record set, and reports what fails. Then run it for two people in Track B who ask you to.

A correct nameserver must do all of these, whatever records it happens to hold:

  • answer at all, asked from a machine that is not the one it runs on
  • answer the same name whether or not the query carries a trailing dot
  • answer the type that was asked — not a different type it happens to hold for that name
  • say no such name for a name it does not hold — not silence, not an empty answer
  • still be answering on the tenth query, not just the first
  • serve a wildcard name, if the record set has one

You cannot check their data without knowing what it should be, so ask them for the records they were given. That exchange is the point.

Report what failed. Do not fix it for them and do not say where to look. If your report is any good, they will find it themselves — and if it is not, you will learn that too.

Then commit the tester as hackattic/serving_dns/conformance.py. It is worth more than the solver.

B — you wrote a server but never cleared it

You are closer than you think. Stop guessing and bisect it:

  • Is your server reachable from your own laptop right now? If not, nothing else matters.
  • Fetch a problem set and print the records you were given. Read them. How many types are in there? Is any name unusual?
  • Now query your own server for every single one of those records, by exact name and exact type. Not one of them. All of them.
  • The one that does not answer is your bug. You will not find it by reading your code.
  • Ask someone in Track A to test you. Give them your address, your port and the records you were given. An outside prober finds in a minute what you will stare past for an hour.

C — you have nothing yet

Start at Class 10 and work forward. You are behind but this is recoverable in one session — twelve people did the whole thing in an afternoon.

If you still cannot log in, your public key is not on the machine. Generate one, add it to GitHub, wait three minutes. Nobody needs to do this for you.

3. Two questions to ask your own code

Regardless of track. Answer both honestly, in your log.

1In what order does your program do these four things: start listening, fetch the problem, load the records, submit? Write the order down. Then work out what happens if the fetch takes three seconds.
2When a resolver asks your server for a name, what exactly does it send? Not what you think it sends — print it. Then compare it, character by character, with the key in your records table.

More than half the class got the first one wrong and did not notice, because free retries hide it. A third got the second one wrong, and it produces a server that looks perfect and answers nothing.

4. Understand it — and make sure your group does

You should be able to answer these with no notes and no AI. If you cannot, that is the work for today, not the code.

  • A query is not just a name. What else is in it, and why does that change the answer?
  • Why does this challenge need no domain name and no registrar, when every real nameserver has both?
  • Your server does not reply. Name three different causes that look identical from outside, and say how you would tell them apart.
  • What is a wildcard record, and what does your code have to do differently to serve one?
  • Why is 0.0.0.0 not the same as 127.0.0.1?

Then do it out loud, in your group. Take turns. Each person answers two of these to the others — no notes, no screen. The rest decide whether that was an answer or was words arranged to sound like one.

This is not optional and it is not a formality. Your group is three or four people; if one of you cannot explain what the group built, the group does not understand it, whatever the scoreboard says. Some of you have no solver yet — that does not excuse you from this half. The concepts are the same whether or not your code runs.

In your log, name the person you listened to, and the one question your group could not answer between you. If every log in your group reports that nothing was missing, that is a claim — and the viva is where claims get tested.
