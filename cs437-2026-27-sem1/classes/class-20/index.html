3. Before you start (10 minutes)

  1. Install Claude Code if you have not. On a Mac or Linux: 
    curl -fsSL https://claude.ai/install.sh | bash
    On Windows (PowerShell). Install Git for Windows first if you do not have it; Claude Code needs it: 
    irm https://claude.ai/install.ps1 | iex
  2. Get your group’s hackathon repo up to date (clone it if you have not): 
    git clone <your group's hackathon repo URL>
cd <repo folder>
git switch main
git pull
  3. Start Claude Code inside that folder by typing claude. The first time, choose to sign in with your Claude account and use the email your Claude seat was sent to. No seat yet? Sit with a member who has one, but write and commit your own file.
  4. Check it can see your project. Ask: “What command runs this app, and what command runs its tests? Cite the files.” Write the two commands down; you will need them.
  5. Decide who writes which file (first 5 minutes, in your group). Three members, three files: spec-status, test-breaker, new-feature. Whoever finishes first also writes CLAUDE.md. Only one person in your group is active? Tell us in class today.

4. Your file: write it, run it, merge it

  1. Make a branch named after your file: 
    git switch -c class20-<file-name>
  2. Create the folder and the file, and paste the template below into it: 
    mkdir -p .claude/skills/spec-status     # File 1
mkdir -p .claude/agents                 # File 2
mkdir -p .claude/skills/new-feature     # File 3
# File 4 (CLAUDE.md) goes in the top folder
  3. Change the template to fit your repo. We wrote the templates for Group 9’s project (Python). Check every one of these:
    • The test command (from section 3, step 4): e.g. npm test, pytest, python3 -m unittest discover -s tests -v.
    • Where the tests live, and how a test is linked to a statement (a class or a describe named after it, a comment, a file per statement).
    • Where the code lives (app/, src/, server/ ...). The test-breaker uses this folder in its steps 1, 2 and 5.
    • How your statements are numbered (S1, CP-01, R1 ...).
    You can ask Claude to adapt it: “Adapt this file to this repo. Keep its steps; change only commands, folders and names.” Then read what it changed.
  4. Restart Claude Code (type /exit, then claude). A new agent file is only picked up at start. Check yours is listed: /agents for the agent, or type / and look for your skill.
  5. Run it on your repo and check the result yourself. Fix the file until the result is right.
    • spec-status: /spec-status
    • test-breaker: “Use the test-breaker agent on <one of your statement IDs>.”
    • new-feature: first commit your skill file (git add .claude, git commit -m "Class 20: new-feature (<your name>)"), then run /new-feature followed by a request in one sentence. The skill makes its own feature/S<n>-... branch for that trial; afterwards go back with git switch class20-new-feature before you push.
  6. Commit, push, and open a pull request on GitHub titled Class 20: <file> (<your name>). Paste what the run printed into the description. (new-feature: you committed already, so just run the last line, git push -u origin HEAD.) 
    git add .claude          # if you wrote CLAUDE.md: git add CLAUDE.md
git commit -m "Class 20: <file> (<your name>)"
git push -u origin HEAD
  7. Another member reviews and approves it on GitHub, then it is merged. Merging your own pull request without a teammate’s approval does not count.

No tests or code in your repo yet?

/spec-status will say “no test” for every statement: that is the right answer. Use /new-feature to write your first statements, their tests and the code. Write the test-breaker file today and run it once you have code.

File 1: .claude/skills/spec-status/SKILL.md

---
name: spec-status
description: Report which SPEC.md statements are green, red, or untested in this repo. Use when someone asks "where are we", "what is left", "is the spec green", or before opening a pull request.
---

# Spec status

1. Read `SPEC.md`. List every statement ID (S1, S2, ...) with its one-line title.
2. Find the tests for each statement. In this repo a statement's tests live in
   `tests/test_spec.py`, in the class whose name starts with the statement ID
   (for example `S4_NeverMatchedTwice`).
3. Run the whole suite once:
   `python3 -m unittest discover -s tests -v`
4. Print one table, nothing else before it:

   | ID | Statement | Tests | Result |
   |----|-----------|-------|--------|

   Result is **green** (all its tests pass), **red** (any test fails, give the
   first line of the failure), or **no test**.
5. Under the table, at most three lines: the count of green / red / no test,
   and the one statement to work on next (the first red, else the first
   untested).

Do not edit any file. Do not fix anything. This skill only reports.

File 2: .claude/agents/test-breaker.md

---
name: test-breaker
description: Checks whether the tests really protect the spec. Breaks one SPEC.md promise in the code on purpose, runs the tests, reports whether they noticed, then puts the code back. Use before a checkpoint or after tests are written.
tools: Read, Grep, Glob, Edit, Bash
---

You check that this repo's tests are honest. You are given one statement ID
from SPEC.md (or pick the one you think is weakest).

1. Run `git status --porcelain -- app/`. If it prints anything, stop and say so.
   (Uncommitted files elsewhere, such as this agent file, are fine.)
2. Read the statement in SPEC.md and find the code in `app/` that keeps that
   promise.
3. Make the **smallest** change to that code that breaks the promise for a
   real user (for example: allow a gmail.com address; match the same
   request twice). Change code only, never tests.
4. Run `python3 -m unittest discover -s tests`.
5. Put the code back with `git checkout -- app/` and run the tests again to
   confirm they pass.
6. Report in this shape:
   - **Statement:** S?
   - **What I broke:** one sentence, file and line.
   - **Did the tests notice?** yes (name the failing test) / **no**
   - **If no:** the test that should be added, in one sentence.

Never leave the code broken. Never edit tests.

File 3: .claude/skills/new-feature/SKILL.md

---
name: new-feature
description: Turn a plain-English feature request into a new SPEC.md statement, a failing test, and the code that makes it pass. Use when a user or the acceptance run asks for a new feature.
---

# New feature, spec first

Work in this order. Do not skip ahead.

0. **Branch.** Create and switch to a new branch
   `feature/S<n>-<short-name>` (S<n> = the next free statement ID) before
   touching any file.
1. **Restate.** Write the request back as one checkable sentence, in the
   style of the existing statements in `SPEC.md`. If it is ambiguous, ask
   one question and stop.
2. **Spec.** Add it to `SPEC.md` as S<n> and a
   *Test:* line saying how it will be checked.
3. **Failing test.** Add a test class named after the ID in
   `tests/test_spec.py`. Run the suite and show that this new test fails and
   every old test still passes. If the new test passes already, the test is
   wrong: fix the test, not the code.
4. **Code.** Change the smallest amount of code in `app/` that makes it pass.
5. **Check.** Run the full suite. Then run the `spec-status` skill, if it
   is in the repo yet.
6. **Commit** on that branch, one commit, message `S<n>: <statement>`. Do not push and do not merge: a
   teammate reviews the pull request.

Never edit or delete an existing test to make the suite pass.

File 4: CLAUDE.md (top folder; whoever finishes first)

Under 15 lines: what the app is, the one command to run it, the one command to test it, where the code and tests live, and any rule Claude keeps forgetting. The one we wrote for Group 9’s project, as an example:

# Campus cab sharing (Group 9)

Python standard library only. Nothing to install.

- Run:  `python3 app/server.py`  (then open http://localhost:8000)
- Test: `python3 -m unittest discover -s tests -v`
- Spec: `SPEC.md`, statements S1, S2, ... Each has a test class in `tests/test_spec.py` named after it.
- Code: matching rule in `app/matching.py`, storage and rules in `app/store.py`, web app in `app/server.py` + `index.html`.
- Never edit an existing test to make the suite pass.

5. Then make them work for you

  • Run /spec-status. Work on what it says is next.
  • Run the test-breaker on your two most important “never” statements. Where the tests did not notice, add the test it suggests, in a reviewed pull request.
  • New statements: if your spec has fewer than ten statements, add the missing ones with /new-feature. If your spec is complete, it is frozen as of today: try /new-feature on a branch for practice, but do not merge it.

Remember what gets most of the hackathon marks: an app that is deployed and used by people outside your group (Class 19). A useful extra skill once you deploy: deploy, the exact steps that put your app online and check the link works.
