Set up your account

  1. Go to hackattic.com and create an account. Log in with GitHub is the quickest route and you all already have GitHub.
  2. Open the challenge page below. Your access token is shown right there on the problem page — you do not need to go hunting through a settings screen for it. Every request you make is authenticated with it, and it is yours alone.
  3. Register your hackattic username on the setup form. The form has a new field for it, and it checks the username against your public profile at hackattic.com/u/<name>, so a typo will be caught rather than silently recorded. Either the bare username or the full profile URL works. Open the setup form — it loads your existing submission, so you are adding one field, not filling it in again.
  4. Keep the token in a variable or a local file. Do not commit it. Add it to .gitignore before you write a single line. Two of you have already leaked an API key to a public repo this semester; do not make it three.

How a hackattic challenge works

Every challenge on the site is the same three-step loop, and once you have done it once you can do all of them:

  1. GET the problem. You call a URL with your access token and the server replies with JSON — your problem data, generated fresh for you.
  2. Solve it in code. Ordinary programming. Parse the JSON, compute the answer.
  3. POST the solution. You send JSON back to a submission URL, and the server replies telling you whether it was accepted or rejected.

The exact URLs and the exact JSON field names are written on the challenge page itself. Read them there. Do not take them from an AI and do not take them from a blog post — see the rule below.

One thing worth understanding: your problem data is generated for your account. The person next to you gets different numbers. You can share code, you can share approach, you can debug together — but there is no answer to copy, because their answer is wrong for you. This is why we are using this platform.

Today's challenge — Help me unpack

hackattic.com/challenges/help_me_unpack

The site's own warm-up, and the cheapest challenge on the board. You are handed some encoded bytes and asked to read numbers out of them — signed, unsigned, floating point, and one where the byte order is reversed. The challenge page tells you exactly which values it wants and what to call them when you send them back.

It needs nothing but the Python standard library. No pip install, no Docker, no system packages. If you find yourself installing something, you have wandered off.

The puzzle is not the point. The point is the loop: fetch, solve, submit, see it accepted. When your submission comes back accepted, put your hand up so the instructor can count you.

The rule for AI today: check the page, not because the model is wrong

Use AI freely. It will write the byte-unpacking in seconds and there is no reason not to let it.

The thing to watch is the API contract — the exact submission URL, the parameter name, the JSON keys. Ask a model for those and what you get back depends entirely on which model you asked. A strong one, especially one that can read the web, will very likely fetch the challenge page and give you the right answer. A smaller one may give you something assembled from memory: right for a different challenge, or right for how the site worked some years ago, or simply plausible.

Here is the part that matters. Both answers look exactly the same. A confident correct answer and a confident wrong one arrive in the same tone, the same format, the same length. You cannot tell by looking which one you got — and neither can the model, because it does not know whether it is recalling or reconstructing.

So the rule is not "the model will lie to you." It is: when the answer is specific to one system, check it against that system. The challenge page is thirty seconds away and it is the source of truth. That check costs you almost nothing when the model was right, and saves you the entire session when it wasn't.

Concretely: if your submission comes back rejected, re-read the spec on the page and compare it against what you actually sent, before you go back to the model and ask why it failed. Debugging your own code is productive. Debugging a hallucinated field name while asking the thing that hallucinated it is not.

This is worth paying attention to today because it is a real skill and you will be graded on it later. Knowing where a given model is reliable and where it is guessing is exactly what the eval assignment at the end of this course asks you to measure. Start noticing now: when your model got the API right, was it because it read the page, or because it remembered? Put the answer in your log.
