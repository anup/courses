Week 5 Lab · Monday 31 August

Teams, and Git Together

Today you get your project group. Solo git you have done — branches, merges, and your first real merge conflict, you have not. By the end of the session your group has a shared repository, and every member's name got into it the hard way: on a branch, through a pull request, past a conflict.

Step 1 — The huddle

Groups go up on the screen in class. When you find yours:

  1. Find your group members and make a circle.
  2. Introduce yourselves — name, year, what you've built so far in this course.
  3. Pick a captain. The captain owns the group repo and speaks for the group when we ask "where are you?"
  4. Pick a group name. You'll live with it on the dashboard all semester, so choose with care (or courage).
  5. Come back to us with the name and the captain. We record both.

Not in any group on the screen? Come to us — you'll join a group today.

Step 2 — The captain creates the group repo

  1. Captain creates a new private repository named cs437-<your-group-name>.
  2. Add every group member as a collaborator, plus the instructors: anup and arjunarul-iitgn.
  3. Create one file on main: members.md, containing only a heading — # <Group Name> — and commit it.
  4. Turn on branch protection for main: Settings → Branches → add a rule — require a pull request before merging, with at least one approval. If GitHub says this needs a paid plan on private repos, apply for the free Student Developer Pack today; until it arrives, the rule still applies — enforced by us instead of GitHub. The history shows every direct push to main, and we look.

From today, in the group repo: nobody pushes to main. Ever. Every change — including the instructors' — arrives by pull request with a review. This is not ceremony; it is the guardrail that makes it safe to let an AI write code later.

Step 3 — The collision drill

Everyone now adds their own line to the same file. This is engineered to go wrong — that's the lesson.

  1. Every member clones the repo and creates a branch named after themselves: 
    git clone <repo-url>
cd cs437-<group-name>
git switch -c add-<yourname>
  2. Edit members.md: add one line directly under the heading — your name, roll number, GitHub handle. Everyone edits the same spot. Commit and push your branch: 
    git add members.md
git commit -m "add <yourname> to members"
git push -u origin add-<yourname>
  3. First member: open a pull request; a teammate reviews and merges it. Painless. Enjoy it — it's the last painless one.
  4. Everyone else: your PR now shows a conflict — main has moved and your branch edits the same lines. Fix it on your branch: 
    git fetch origin
git merge origin/main     # conflict appears in members.md
# open the file: keep BOTH lines — theirs and yours — remove the <<< === >>> markers
git add members.md
git commit               # completes the merge
git push
    Then get your review and merge. The next member conflicts again — on purpose. Take turns; everyone resolves at least one conflict with their own hands.
  5. Last member, do it differently: instead of merging main into your branch, rebase: 
    git fetch origin
git rebase origin/main    # same conflict, resolved the same way
git add members.md
git rebase --continue
git push --force-with-lease
  6. Now look at what you built: 
    git log --oneline --graph --all
    Find the merge commits (diamonds) and the rebased commit (a straight line). Same result, two shapes of history — discuss in the group which you'd rather read six weeks from now.

Done when

  • members.md on main lists every member — and every line got there through a reviewed pull request.
  • Every member resolved at least one conflict themselves.
  • The captain has given us: group name, captain, repo link.
  • Your personal log for today is in your own repo: lab-notes/week-05.md, same format as last week. One honest paragraph on the conflict you resolved beats a page of ceremony.

The rule for AI today: explain, don't drive

Today git is by hand — the whole point is to feel the conflict and fix it yourself. You may ask your AI to explain anything — "what does rebase actually do?", "what do these <<<<<<< markers mean?" — but the commands and the conflict resolution are yours. If the AI resolves your conflict, you didn't have one.
