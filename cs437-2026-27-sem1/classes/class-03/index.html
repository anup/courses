Git — Your Time Machine

Learn Git by using it on the Bug Dodger game you built in Class 1. Follow the steps at your own pace. Break things on purpose, then rewind. Ask an instructor whenever you are stuck.

Today's Goals

  1. Get your system signed in to GitHub and your Class 1 game ready.
  2. Use Git on that game: make checkpoints, see what changed, break it, and rewind it.
  3. Push it online, try a branch and a review, and let the AI make one commit while you supervise.

You will not memorise commands. You will do each thing through VS Code or by asking Copilot, and understand what it means. The commands are shown so you recognise them — not so you learn them by heart.

Before You Start

Can you already push to your GitHub repo from Class 1?

  • Yes — open your repo in VS Code and jump to Step 1.
  • No, or you missed Class 1 — do the setup below first.

Setup (Class 1 catch-up)

  1. Follow the Class 1 handout: install Git, apply for GitHub Education + Copilot, and build the Bug Dodger game.
  2. Sign in to GitHub inside VS Code (this is all the authentication you need — no SSH keys): click the Accounts icon at the bottom-left, choose Sign in with GitHub, and approve in the browser.
  3. Open your ai-assisted-software-development-lab folder in VS Code.

Copilot not approved yet? That is fine for today. Ask an instructor for a ready-made copy of Bug Dodger and do every Git step below on it — the Git learning does not wait on Copilot.

1. Make Your First Checkpoint

A commit is a checkpoint: the whole project saved at a moment you choose, so you can return to it later.

  1. Open the Source Control panel in VS Code (the branch icon on the left bar).
  2. Stage your changes (the + next to them), type a message like checkpoint: working game, and click Commit.

Or ask Copilot: "Commit everything with the message 'checkpoint: working game'."

git add .
git commit -m "checkpoint: working game"
git status   # read this: it should say your working tree is clean

Run git status (or read the Source Control panel) whenever you are unsure what Git is doing. It almost always answers the question.

2. Change Something, and See It Before You Save

Make one small, visible change — for example, change the game's title text, or a colour in style.css.

  1. In the Source Control panel, click the changed file. VS Code shows the old and new lines side by side — that is git diff. Read it.
  2. Commit with a clear message, e.g. change background colour.

The habit that matters: always look at what changed before you commit — especially when the AI made the change.

3. The Rewind (the important one)

Break your game on purpose. Your instructor will give your team something to try (a small edit to game.js or style.css). Save the file and open the game — watch it fail.

Now bring it back:

  1. In Source Control, right-click the broken file and choose Discard Changes — that is git restore. It returns the file to your last checkpoint.
  2. Open the game again. It works.
git restore game.js   # throw away changes since the last checkpoint

It does not matter how badly you broke it — a loud crash or a subtle wrong-feeling bug. One restore takes you back to the last good checkpoint, every time. This is why you keep checkpoints: the day the AI makes a mess, you rewind.

One limit, worth knowing: restore only brings back what you committed. If you never checkpointed, there is nothing to go back to.

4. Push It Online

Push copies your checkpoints to GitHub — the shared copy in the cloud that your teammates and instructors can see.

  1. In Source Control, click Sync / Push (the first time, it may offer to publish the branch — accept).
  2. Open your repository on github.com: your latest commit and its message are there.
git push

5. A Branch: Let the AI Try Something Big — Safely

A branch is a safe parallel copy of your code. Reach for one when you want to try something risky without touching your working game — for example, letting the AI add a whole start screen or a new level. If it turns into a mess, you throw the branch away and your working version never knew. If it is good, you merge it. (Branches are also how you and a teammate change the same game at once without overwriting each other.)

  1. Create a branch — ask Copilot: "Make a branch called feature/start-screen," or use the Source Control menu.
  2. On that branch, ask the AI for the big change (a start screen, say). Run the game, then commit it.
  3. Push the branch and open a Pull Request on GitHub. Ask a teammate to read it, leave one comment, then merge.
  4. Your main stayed working the whole time. Risk lived on the branch.

Reading a change and deciding whether it is good — that review is the core skill of this whole course.

6. Let the AI Commit — Then Read What It Did

  1. Ask Copilot: "Add a start screen to the game, then commit it with a clear message."
  2. Open the diff of its commit. Do you understand every line it changed? Does its message actually match what it did?

The AI can run Git for you. Your job is to check it — this is your first taste of supervising an agent. If its message says "update code," tell it to do better.

7. Update Your AI Log

Open lab-notes/week-01.md (or start week-02.md) and record, in your own words:

  • what you asked the AI,
  • what it produced,
  • what you changed yourself,
  • how you verified it worked,
  • and one thing you still do not understand.

Commit and push the log. The log is where you show your thinking — it matters as much as the code.
