Pointers in C

Every variable sits somewhere in memory, and that somewhere has a number. &x hands you the number; *p goes back to it. Once you have both, a function can finally change a caller's variable — which is what scanf has been quietly doing with &a since Class 02. From there the rest follows: an array passed to a function is just a pointer to its first element, so A[i] is only ever shorthand for *(A+i), and arithmetic on pointers counts in elements rather than bytes. Then the harder question — where does memory live, and for how long? A local dies when its function returns, which is why returning its address is a bug; malloc gives you memory that outlives the call, and it is yours until you free it.

Work through the snippets first

Before the practice problems, make sure you can predict the output of these without running them. If you can, the rest of the topic is downhill.

  • Snippets 4, 5, 6 — three attempts at a function that adds 1 to a variable. The first fails because it got a copy; the second fails because it moved the pointer instead of following it; only the third writes through with *a = *a + 1. Understand why each does what it does.
  • Snippet 8 — a function assigns to A[1] and the caller's array changes. Nothing was copied.
  • Snippet 11 — +1 moves an int* by 4, a char* by 1, a double* by 8. Pointer arithmetic counts elements, never bytes.
  • Snippet 21 — a function returns the address of its own local array. The compiler warns; the pointer dangles the moment the function returns.
  • Snippet 31 — why int* p, q; does not declare two pointers. The * binds to the name, not the type.
  • Paper exercise: for int num[5] and int *p = num, write down four different expressions that all read num[3]. There are more than four.

The thread through the lecture deck

The slides build one idea at a time, each answering the question the previous one raised:

  • Pass by value — sum(a, b) gets copies, so the parameters are not the caller's variables. scanf needs &a precisely because it has to write back.
  • Arrays are the exception — sum(num, 5) copies nothing. A is a pointer to num[0], so the function reads your array directly, and a pointer carries no length, hence the separate n.
  • Four ways to write the same function — int A[] or int *A in the signature, A[i] or *(A+i) in the body. All four compile to the same thing.
  • Reverse with two pointers — left and right start at the ends and walk inward, swapping. Because the array arrived as a pointer, the swaps land in the caller's array.
  • Returning an array — the create() that returns a local array is broken: num dies when create returns. malloc fixes it, and the caller then owes a free.
  • Growing an array — add() allocates one slot bigger, copies, appends. In a loop, that reads input of unknown length.

Practice — two pointers walking an array

Snippet 17 reversed an array with two pointers starting at opposite ends and walking inward. That pattern solves a whole family of problems, and every one below is a variation on it. Write them in C with pointers rather than indices, even where indices would be easier — the point is fluency with *left, left++, and left < right. Full topic list on the practice page.

  • 344. Reverse String — snippet 17 almost verbatim, on a char array.
  • 125. Valid Palindrome — the same two pointers, but they compare instead of swapping, and skip non-alphanumeric characters.
  • 167. Two Sum II — ends inward again: too small means move left up, too large means move right down.
  • 283. Move Zeroes — both pointers start at the left and move at different speeds.
  • 26. Remove Duplicates from Sorted Array — one pointer reads, one writes; the gap between them is what you removed.
  • 11. Container With Most Water — harder: the ends-inward walk again, but you have to argue why moving the shorter side is safe.

Practice — writing through a pointer

These need a function to modify the caller's data rather than return a new value — snippet 6's pattern.

  • 189. Rotate Array — rotate in place. The neat solution is three reversals, so snippet 17's reverse is your building block.
  • 88. Merge Sorted Array — merge into the first array's spare room. Walking backwards from the end avoids overwriting what you have not read yet.
  • 27. Remove Element — read and write pointers; advance the reader alone when you drop a value.
  • C exercise, no judge: write void swap(int *a, int *b) and use it to shorten snippet 17's reverse. Confirm the caller's array really changed.
  • C exercise, no judge: write void min_max(int *A, int n, int *min_out, int *max_out), returning both answers through pointer parameters — the standard way a C function returns two things.

Practice — memory that outlives the function

Snippets 21 through 30 are about lifetime: stack memory dies with the function, the heap lasts until you free it. No judge for these — write them, run them, and check for leaks.

  • Fix snippet 21. Make create() return an array the caller can actually use, and have the caller free it.
  • Read an unknown number of integers until -1, storing them all (snippet 29). Then count how many element copies your program did for 1000 inputs. It should be about 500,000 — which is why doubling the capacity matters.
  • Write int *concat(int *A, int n, int *B, int m) returning a freshly allocated array holding A then B. Check for NULL, and be clear about who owns the result.
  • Write remove_at from snippet 30, then handle the edge case the snippet skips: n == 1, where malloc(0) is the wrong answer.
  • Run one of your malloc programs without the matching free. On macOS, leaks -atExit -- ./a.out will tell you what you lost.
  • From the lecture deck: read positive integers until -1, one per line, and print them in reverse, growing the array with add as you go. Mind the order inside the loop — allocate the new block, then free the old one, then reassign.
  • From the lecture deck: int *removeAt(int *arr, int n, int index), returning a new array with that element gone.
