Lower Bounds on Comparison-Based Sorting

Merge sort, heap sort, and quick sort all land at O(n log n). Can any comparison-based sort do better? No — and we can prove it for every such algorithm at once. Model the algorithm as a binary execution tree: each comparison branches two ways, and each of the n! input orders must reach its own leaf. A binary tree with n! leaves has height at least log₂(n!) = Ω(n log n), so some input forces that many comparisons. The escape hatch: stop comparing. When keys are small integers, counting them sorts in O(n).

Practice — beating the bound

The theorem says no comparison sort beats Ω(n log n) — so every problem below dodges it by not comparing. Whenever the keys are bounded integers, count them instead. Full topic list on the practice page.

  • 75. Sort Colors — only three possible values: count them and rewrite the array in O(n). Compare with your partition solution from Class 05.
  • 912. Sort an Array — values fit in a fixed range; write counting sort and beat your earlier O(n log n) submissions.
  • 1122. Relative Sort Array — values at most 1000; one counting array handles both the given order and the leftover tail.
  • 274. H-Index — bucket papers by citation count for O(n), where sorting first costs O(n log n).
  • 164. Maximum Gap — hard: linear time via buckets, even though it looks like it needs a full sort.
  • Paper exercise: draw the complete execution tree for sorting three numbers a, b, c. Check it has 3! = 6 leaves and height 3 — matching ⌈log₂ 6⌉ — so 3 comparisons are unavoidable in the worst case.
